# Super Agent Memory And Source Seeding Design

## Purpose

Seed the LWT super agent with durable retrieval memory and source evidence for supplier operations, shopper behavior, content strategy, and market/social listening. This is retrieval memory, not model fine-tuning. The agent should answer and plan from approved, attributed, sanitized records stored in the LWT Supabase project.

## Scope

The first seed batch includes internal LWT Intelligence Center documentation, source configuration, aggregate shopper behavior samples, existing seeded source summaries, and curated market/social listening prompts. Social data is stored only as attributed market-signal summaries from official APIs, manual exports, or human-curated observations. Raw social feeds, private messages, scraped platform data, customer-level shopper behavior, and unrestricted email content are out of scope.

## Architecture

The source of truth is the existing `agent_memory_documents` and `agent_memory_chunks` tables. Seed definitions live in repo-owned JSON and Markdown files, and a local generator converts those files plus selected internal docs into deterministic SQL. The generated SQL upserts memory documents and replaces their chunks, so the seed can be re-run safely without duplicating records.

Seed categories:

- `business_note`: internal operating rules, source policy, dashboard setup, and super-agent constraints.
- `market_signal`: curated social/market listening summaries and official-source watchlists.
- `catalog_report`, `seo_report`, `product_report`: structured internal reports when they are added later.
- `inventory_output`: generated by supplier sync, already supported by the app.

## Data Flow

1. Internal docs are read from `docs/LWT_INTELLIGENCE_CENTER_*.md`, `README.md`, and selected config/import files.
2. Curated source seeds are read from `config/super-agent-memory-seeds.json`.
3. The SQL generator sanitizes text, truncates long content, escapes SQL values, and creates chunks.
4. SQL is applied only to `lwt-intelligence-staging` (`udqjdegsqxfvaocuuvab`).
5. Verification queries check document count, chunk count, source types, sensitivities, and sample titles.

## Guardrails

No JRS database. No Shopify storefront/theme edits. No pixels. No live GA4 or Search Console ingestion in this phase. No blog publishing, customer emails, price changes, purchase orders, or platform scraping. No customer-level tracking or raw PII. Social content must have provenance and should be summarized before storage.

## Access Pattern

Agents retrieve memory through `/api/memory/search` when Render is configured, or directly through Supabase-backed repository methods in worker/runtime contexts. Until Render has `DATABASE_URL` and `INTERNAL_DASHBOARD_PASSWORD`, direct Supabase seeding and SQL verification remain the operational path.

## Testing And Verification

Run the generator locally and apply the output to the LWT Supabase project. Verify:

- Memory documents exist by source type.
- Chunks exist for every document.
- Sensitivity is `internal` or stricter unless content is intentionally public.
- Search-relevant titles include LWT Intelligence docs, source policy, shopper behavior samples, and curated market/social topics.
